# Ghost of Yōtei в KytyPS5 на Windows: план запуска

Дата исследования и интеграции: **5 сентября 2026 года**. Игра: **Ghost of Yōtei, PPSA26344**.

Цель — последовательно довести игру от воспроизводимого отказа при запуске до
управляемой игровой сцены на Windows. Сборка эмулятора — первый самостоятельный
результат. Успешная сборка и прохождение тестов сами по себе не означают, что игра
запускается или пригодна для прохождения.

## 1. Зафиксировать исходную сборку Windows

Проверенный компьютер: Windows 11 Pro, сборка 26200; Ryzen 9 5950X; 64 ГБ RAM;
GeForce RTX 4060, **8188 MiB VRAM (около 8 GiB)**, драйвер **610.88**,
Vulkan **1.4.341**. Диагностика подтвердила требуемые эмулятором Vulkan features;
`maxComputeWorkGroupSize = (1024, 1024, 64)`,
`maxComputeWorkGroupInvocations = 1024`. Результат сохранён локально в
`_Build/host-vulkan.txt`.
Эти данные описывают стенд и не являются подтверждёнными требованиями игры.

Исходная ревизия для сравнения — upstream `main` на коммите **`74a78f3`**.
Исходная установка сохраняется в `_Build/windows/baseline-74a78f3`;
`_Build/windows/install` предназначен для новой сборки с интегрированными патчами.
Ревизию каждого запуска нужно записывать вместе с журналом.

Нужны Git, CMake, Ninja, Visual Studio/Build Tools 2022 с Windows SDK и C++
toolchain, `clang-cl`, а также Qt 6 для MSVC 2022 x64 с Concurrent, Network и
Widgets. Использовать нативное окружение сборки Windows из x64 Native Tools
Command Prompt или Developer PowerShell. `cl.exe` проектом не поддерживается.

На стенде определены `clang-cl 18.1.8`, Ninja 1.12.1, CMake 3.31.5,
VS 2022 с MSVC toolset 14.42.34433 и Windows SDK 10.0.26100.0.
Для текущей сборки установлены переносимые Qt 6.10.3 (qtbase, qttools, qtsvg)
и glslang 16.5.0 в `_Build/tools`. Qt получен через aqtinstall с зеркала Qt
dotsrc с проверкой опубликованных SHA-1 архивов; glslang — из релиза Khronos.

Дополнительно нужен компилятор glslang: Windows-раздел README его не перечисляет,
но корневой CMake ищет **`glslangValidator`**. В выбранном архиве программа
называется **`glslang.exe`**, поэтому её полный путь
`_Build/tools/glslang-16.5.0/bin/glslang.exe` передаётся через
`KYTY_GLSLANG_VALIDATOR`. В Windows CI используется
`vcpkg install glslang[tools,opt]:x64-windows`. См. [README](../README.md),
[CMake](../CMakeLists.txt) и [Windows CI](../.github/workflows/build.yml).

Зависимости из [3rdparty](https://github.com/fxpw/KytyPS5/tree/main/3rdparty)
обеспечивают Vulkan и работу с SPIR-V, окно/ввод/аудио (SDL2), декодирование
медиа (FFmpeg/LibAtrac9), журналирование и профилирование. CMake дополнительно
получает закреплённые xbyak и Zydis для работы с x86-кодом. Это инфраструктура
эмулятора; игровые исправления из #490 и DPP8 находятся в `src`, а не в этих
библиотеках. Submodules инициализировать на закреплённых коммитах:

```powershell
git submodule update --init --recursive
git submodule status --recursive
```

Массовое обновление submodules до последних версий не входит в подготовку
стенда: оно изменит основу эксперимента и затруднит поиск причины регрессий.

Команды повторной сборки из корня репозитория в x64 Developer PowerShell:

```powershell
$glslangPath = (Resolve-Path "_Build/tools/glslang-16.5.0/bin/glslang.exe").Path
$qtPath = (Resolve-Path "_Build/tools/Qt/6.10.3/msvc2022_64").Path
cmake -S . -B _Build/windows -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang-cl -DCMAKE_CXX_COMPILER=clang-cl -DCMAKE_PREFIX_PATH="$qtPath" -DKYTY_GLSLANG_VALIDATOR="$glslangPath" -DKYTY_BUILD_LAUNCHER=ON -DBUILD_TESTING=ON
cmake --build _Build/windows --target launcher kyty_tests --parallel
ctest --test-dir _Build/windows --output-on-failure
cmake --install _Build/windows --prefix _Build/windows/install
```

Цель `kyty_tests` нужно собирать явно: тестовые executable объявлены с
`EXCLUDE_FROM_ALL`, поэтому обычная сборка не подготовит их для полного CTest.

## 2. Получить воспроизводимый запуск самой игры

Официальные варианты получения игры — [PlayStation Store](https://store.playstation.com/en-us/concept/10003923)
и [диск PS5 в PlayStation Direct](https://direct.playstation.com/en-us/buy-games/ghost-of-yotei-ps5).
Это американские витрины; доступность зависит от региона. На проверенной
[странице Sony](https://www.playstation.com/en-us/games/ghost-of-yotei/) указана PS5;
официального скачивания готовой папки для эмулятора не найдено. Покупка игры
не выдаёт расшифрованный дамп для KytyPS5.

Подготовить собственные законно полученные файлы игры в формате, поддерживаемом
загрузчиком. Проверить наличие исполняемого файла и полноту данных, записать
serial, версию игры и установленного обновления. Для сравнения с #281 особенно
полезен вариант `PPSA26344`, `1.008.000`; другой вариант требует нового исходного
лога и может давать другую последовательность ошибок.

На чистой сборке `74a78f3` выполнить один контролируемый запуск с сохранением
полного `_kyty.txt`. Зафиксировать GPU, драйвер, Vulkan limits, параметры запуска,
первый отказ, shader hash, PC и raw words. Для графических экспериментов включать
Vulkan/SPIR-V validation; её доступность и отсутствие сообщений проверять явно.
Журналирование по умолчанию отключено. Пример первого запуска после появления
полной папки игры с `eboot.bin`, `sce_sys/param.json` и остальными данными:

```powershell
New-Item -ItemType Directory -Force "_Build/runs/yotei-baseline" | Out-Null
& ".\_Build\windows\baseline-74a78f3\kyty_emulator.exe" --game "D:\Games\GhostOfYotei" --printf-direction File --printf-output-file "_Build/runs/yotei-baseline/_kyty.txt" --shader-validation true --shader-log-direction File --shader-log-folder "_Build/runs/yotei-baseline/shaders" --shader-optimization-type Performance
```

Заменить путь к игре фактическим. Затем повторить запуск на интегрированной
сборке из `_Build/windows/install`, сохранив журнал в другой папке. Каждому повтору назначать новую папку журнала:
логгер перезаписывает прежний файл. Размер окна не считать внутренним разрешением
рендеринга игры; `--redzone` и прочие обходы проверять отдельными опытами по логу.
На стенде **Khronos validation layer пока не установлен**. Его подготовка —
отдельный шаг диагностики после исходной сборки; отсутствие слоя не препятствует
самой сборке и обычному запуску, но такой запуск нельзя считать проверкой Vulkan
validation. Логи сохранять отдельно для каждой ревизии и конфигурации.

Критерий завершения: есть собственный повторяемый отказ и минимальный набор
данных для анализа. Если первым окажется другой сбой, исправлять нужно его,
сохраняя #281 как исторический ориентир.

## 3. Проверить IMAGE_ATOMIC_FMIN/FMAX на игре

Код #490 и исправление `numeric_class` уже включены в fork. Для CAS-представления
атомика согласованы `Uint`, `R32ui` и `R32Uint`; float min/max вычисляются над
битовым представлением. Регрессии проверяют реальные raw words, ненулевой
R32F-дескриптор, возврат старого значения, специальные значения и конкурентные
обновления. Исходники проверок: [GPU-сценарии](../tests/ShaderRecompilerComputeTests.cpp)
и [материализация ресурсов](../tests/ResourceMaterializationTests.cpp).

После успешных Windows-проверок повторить запуск игры и сравнить полный журнал
с `74a78f3`. Критерий прохождения игрового препятствия — конкретный шейдер
проходит прежний отказ и новый результат подтверждён логом. Исторические
«2 шейдера» не являются обязательным числом на другой ревизии или версии игры.

## 4. Проверить DPP8 и его ограничения

Декодирование DPP8/DPP8FI, IR и SPIR-V subgroup shuffle перенесены из #338/#340.
Поддержаны VOP1, VOP2 и VOPC, дополнительное слово с `8 × 3-bit` selectors и
escape-коды `0xe9`/`0xea`. Перестановки ограничены каждой группой из восьми lanes;
режим FI0 подставляет ноль при чтении из lane с выключенным guest EXEC, FI1
читает прежнее значение. Запись результата сохраняет неактивные destinations.
Семантика FI описана в [документации LLVM](https://llvm.org/docs/AMDGPUModifierSyntax.html#dpp8-modifiers).

**Известное ограничение общей модели исполнения:** `S_CBRANCH_EXECZ` сейчас
ветвится отдельно для каждой host invocation. Если такая ветка исключила
неактивный lane из исполнения SPIR-V, FI1 внутри неё не может надёжно получить
его прежний VGPR через subgroup shuffle. Это также относится к существующему
DPP16. Текущие DPP8-тесты проверяют inactive EXEC без исключающей host-ветки;
их успешность не доказывает корректность этого случая. Потребуется отдельная
работа над моделью ветвления и регрессия с такой веткой.

Дополнительно проверка чтения VCC целиком через `S_MOV_B32` выявила существующее
ограничение `Translator::BallotMask`: вместо упакованной маски возвращается
локальный бит. Эта часть модели масок не изменена переносом. Регрессия DPP8
проверяет каждый бит VCC через `V_CNDMASK_B32` при восстановленном полном EXEC;
корректность скалярного чтения всей маски остаётся отдельной задачей.

После тестов и валидации SPIR-V повторить запуск той же игры. Исторические
22 скомпилированных шейдера — ориентир для сравнения; прогресс именно этой
сборки нужно подтвердить собственным журналом.

## 5. Разобраться с размером compute workgroup

При воспроизведении `LocalSize Z 256 > device max 64` сохранить конкретный shader,
guest-регистры dispatch/workgroup и subgroup properties RTX 4060. На текущем
стенде уже измерен предел Z=64 при общем пределе 1024 invocations; это согласуется
с ограничением из старого отчёта, но ещё не подтверждает, что текущая версия игры
достигает именно этого сбоя.

Сначала определить, действительно ли игра задаёт Z=256, либо размеры и порядок
осей искажены при декодировании metadata или команд GPU. Исправление декодирования
предпочтительно, если ошибка находится там. Если размер действительно превышает
предел устройства, потребуется обоснованное преобразование dispatch/shader.

Такое преобразование должно сохранять наблюдаемые guest-программой
`LocalInvocationId`, `LocalInvocationIndex`, `GlobalInvocationId`, workgroup IDs,
обращения к shared memory, атомики и барьеры. Простое ограничение Z до 64 меняет
вычисление. Разделение одной workgroup на несколько требует отдельного решения
для shared memory и синхронизации, поэтому не является универсальным обходом.

Критерий завершения: проблемный dispatch проходит validation и даёт правильные
результаты на тестах, чувствительных к индексам, shared memory и барьерам; игра
проходит прежнюю точку остановки.

## 6. Продвигаться по наблюдаемым результатам

После каждого этапа фиксировать следующий первый сбой. Заранее утверждать,
что после перечисленных исправлений игра заработает, нельзя: дальнейшие участки
движка могут требовать новых GPU-инструкций, ресурсов, системных функций или
исправлений синхронизации.

| Этап | Что считается результатом |
| --- | --- |
| Сборка | Windows-приложение установлено и запускается; результаты тестов сохранены. |
| Начальная загрузка | Игра проходит исходные отказы шейдеров; прогресс виден по полному логу. |
| Первый кадр | Получен настоящий кадр игры и подтверждён его вывод; окно эмулятора само по себе не считается. |
